# 麦麦省钱打法手册

本手册是"省钱助手"的领域知识底稿 —— 讲清楚**钱到底漏在哪**，以及每一步为什么这么做。

---

## 一、钱漏在四个地方

```
① 没领的券       麦麦省里有券没领，白丢
② 领了用不对     券在手，但下单时没用 / 用错组合
③ 积分睡大觉     积分到期归零，或换了性价比最差的
④ 挑错时机       同样的东西，活动期买便宜一截
```

对应四步动作：**领 → 算 → 换 → 择时**。

---

## 二、领：先把白送的拿走

`available-coupons` → `auto-bind-coupons`。

- 领券是**零风险正收益**（券不要钱，过期也无损失），没有理由不领。
- 但要清楚：**领到的券 ≠ 能用**。券包是"所有权"，能不能核销取决于**门店 + 下单方式 + 时间**。
  实测中券包 5 张，在某一门店的到店自取场景下只有 1 张可用。

**要点**：领完必须做一次"券包体检" —— 本店可用几张、几张没到使用时间、几张即将过期。

---

## 三、算：券的最优用法（本 Skill 的核心）

### 3.1 为什么不能靠推理

麦当劳的券叠加规则、门槛判定、互斥关系全在**服务端黑盒**里：
- 同一订单能否用两张券？
- 套餐券和单品券能否叠加？
- "用券价"和"满减"是否互斥？

靠本地写规则去推，必然错。**唯一可靠办法是拿官方价格引擎试算。**

### 3.2 正确姿势：生成 → 剪枝 → 试算

```
本地（coupon_optimizer.py）           服务端（calculate-price）
  归一化券，估算纸面收益
  生成候选方案（单券/组合/凑单）
  按估算收益排序、剪枝到可控数量
        │
        └──────────── 逐个真实试算 ────────→  data.price = 权威实付
                                              ↓
                                        取最低者定案
```

**为什么本地估算不可信但仍有用？** 本地估算只用来**决定先试算谁**（否则方案数会爆炸），
最终金额一律以服务端为准。这是"搜索本地化、定价服务端化"的分工。

### 3.3 券的四种典型形态

| 形态 | 券面特征 | 本地能否估算 | 识别依据（实测） |
|---|---|---|---|
| 指定价购 | `discountDesc = "用券价格"` | ✅ 能 | `discountInfo.discountValue` |
| 免费兑换 | `ifFreeCoupon = true` / 券名带"免费" | ✅ 能 | 券名 / 标志位 |
| 满减 | 券名带"满N减M" / `reducePrice` | ✅ 能 | 券名正则 / `reducePrice` |
| 折扣 | 券名带"N折" | ✅ 能 | 券名正则 |
| 买赠 | 券名带"买一送一" | ⚠️ 部分 | 券名正则 |

**注意**：真实的 `available-coupons` 返回**不含面额**，此时一律标 `confidence=trial` 送试算，
绝不凭券名编一个折扣数字糊弄用户。

### 3.4 两个高价值判断

**① 凑单净收益**（很多人想不到）
满减券差一点达标时，"加购一件"可能反而更省：
```
购物车 92 元，券「满100减20」→ 差 8 元
加购 9 元薯条 → 实付 92+9-20 = 81 元 < 92 元
净省 11 元
```
脚本会算 `净收益 = 多减的金额 − 加购成本`，只推荐净收益为正的。

**② 买赠凑件**
买一送一、购物车只有 1 件时：
```
把商品加到 2 件 → 付 1 件的钱拿 2 件 → 实付不变，多得 1 件
```
前提是用户**确实需要 2 件**，所以必须把这个前提讲明白，不能当成纯收益推荐。

## 四、换：积分按"每分价值"花

### 4.1 一把统一的尺子

积分没有统一标价，所以要换算成 **元/积分**：

```
每积分价值 = 商品现金价值（元） ÷ 所需积分
```

实测示例：
| 兑换项 | 积分 | 现金价值 | 元/分 |
|---|---|---|---|
| 免费脆薯饼券 | 100 | 9 元 | **0.0900** |
| 麦辣鸡腿堡券 | 400 | 24 元 | 0.0600 |
| 复古棒球帽 | 3000 | 30 元 | 0.0100 |

→ 结论：换餐券远优于换周边。**同样的积分，价值差 9 倍。**

### 4.2 抽奖怎么判断（机会成本法）

抽奖是概率收益，不能和确定性兑换直接比。用**机会成本**作桥：

```
低效率抽奖成本 = 消耗积分 × 最优兑换的元/分
（这堆积分如果不抽奖、拿去最优兑换，能值多少钱）

→ 只有当「期望奖品价值 ≥ 这个数」时，抽奖才划算。
```

实测示例：抽奖耗 24 积分 × 0.09 元/分 = **2.16 元** 的盈亏平衡线。
即"期望奖品得值 2.16 元以上"才值得抽。

> 官方不公开中奖概率，所以本 Skill 给出的是**盈亏平衡线**而不是一个编造的期望值 —— 这是诚实的做法。

### 4.3 过期压倒一切

本月将过期的积分，**即使单位价值低也要优先花掉**：归零的价值是 0，任何正收益都优于 0。
`query-my-account` 的 `currentMouthExpirePoint` / `nextMouthExpirePoint` 是必看字段。

## 五、择时：活动期下单

`campaign-calendar` 返回当月日历（往期 + 今天 + 未来）。用法：
- **今天**有什么（`today: true`）
- **接下来几天**有什么值得等

常见节奏（结合活动信息判断，不硬编码）：
- 早餐时段（约 05:00–10:15）有早餐专属价
- 工作日与周末活动不同
- 新品/联名活动首日常有限量或首购优惠
- 会员日、抽奖活动日

**判断原则**：如果用户想买的东西，两天后有更划算的活动，就明确告诉他"再等等"。
省钱不只是"这一单怎么最便宜"，还包括"什么时候买"。

## 六、场景参数的坑（一定要记牢）

| 场景 | beType | orderType | beCode |
|---|---|---|---|
| 到店自取 | 1 | 1 | **不传** |
| 得来速 DT | 5 | 1 | **必传** |
| 麦乐送 | 2 | 2 | **必传** + addressId |
| 企业团餐 | 6 | 2 | **必传** + gmServiceCode |

- `beCode` 是否传错，是最高频的错误来源。
- `takeWayCode` 不能猜，必须取 `calculate-price` → `data.takeWayList[].code`。
- `reservationDate` 格式 `yyyy-MM-dd HH:mm`，**仅预约场景传**。

## 七、判断优先级（决策顺序）

```
1. 有券快过期吗？        → 有，优先为它设计订单
2. 本店这个场景有可用券吗？→ 没有，考虑换场景（到店 vs 外送）
3. 券能不能叠加？        → 试算，别猜
4. 差一点达标要不要凑？   → 算净收益，> 0 才凑
5. 积分快过期吗？        → 先花快过期的
6. 过两天有活动吗？      → 有就等
```

## 八、绝不做的事

- ❌ 用本地推算的金额当作"实际要付的钱"告诉用户
- ❌ 把 `available-coupons` 的券直接拿去下单（会因缺 couponId 被拒）
- ❌ 未展示活动信息就执行 `draw-lottery`
- ❌ 把"估算"和"真实试算"混在一起展示，不区分
- ❌ 把用户 MCP Token 写进任何公开文件
